Start here / Your task

Search one PRD line item for related code and tests

Use the line item to choose a short, distinctive search phrase. Select the repository whose implementation you want to inspect. The command below searches its requirement, code, and test indexes together.

Keep 2–5 distinctive terms; the correlator uses only the first eight terms. This page builds a command but does not run it or send your text anywhere.

cd ~/prd-code-rag-lab
python3 lab.py correlate --repo scorecard --query 'force push' --limit 10
  1. Run the generated command in your terminal. Check candidates.requirement, candidates.code, and candidates.test; use --limit 10 to see beyond the first few hits.
  2. Open the cited paths and line numbers under data/<repo>/. Decide whether the code implements the whole line item and whether a test asserts that same behavior. Shared words alone are not enough.
  3. If the line is from already indexed source documentation, the requirement candidate can cite it. For the example above, expect docs/checks.md:88-90 or docs/checks.md:109-111, plus the force-push probe and tests. The reviewed Scorecard case demonstrates a final proof.
If this is your own, unindexed PRD: its text acts only as the search query. Requirement results come from the selected repository's docs, not your PRD. The lab cannot yet cite your PRD line or issue a verified implementation verdict for it. To do that, you would need to add your PRD as an indexed, pinned requirement source, review the code/test citations, create a case, and register a claim-specific proof. See the extension guide. The automatic new-PRD workflow is scoped in Phase 2.
Before you run it / Resources and risk

What does setup pull, and will it fit?

On a fresh clone, bash bootstrap.sh checks for Python 3.12+, Git, and Go 1.21+. It does not install them or Ollama. It downloads only three pinned open-source repositories, builds the Go chunker and nine SQLite indexes, then runs 15 lab tests and the retrieval benchmark. ollama pull qwen2.5:1.5b is a separate, optional step for local model runs.

ItemMeasured hereRequired?
HTTPX + Scorecard + Pluggy source checkoutsAbout 111 MB combinedYes, bootstrap downloads them
Nine indexes + Go chunkerAbout 4.5 MB combinedYes, bootstrap builds them
Qwen2.5 1.5B model986 MB downloadOnly for --mode local
Installed Ollama runtimeAbout 2.1 GB libraries + 37 MB binary on this machineOnly for --mode local; install separately

For your 12 GB RAM / 2 GB VRAM / older i5 machine, offline mode needs no GPU. One local model run here used about 0.8 GB runner RAM and 1.0 GB additional VRAM, with a 4,096-token context; the CPU/GPU split varies. Keep roughly 3–4 GB RAM available, run one model at a time, and allow tens of seconds per local case. Aim for at least 2 GB free disk for offline setup with prerequisites installed, or 6–8 GB for a first-time Ollama plus model setup.

Security boundary: bootstrap executes this repo's scripts and imports pinned Pluggy in one test; inspect code and do not use sudo. GitHub clones and optional model pulls require network, but lab model calls go to 127.0.0.1:11434. Keep Ollama bound to localhost. Source passages can mislead the model, RBAC principals are selectable locally, and traces or shell history may retain supplied text. Do not put secrets in PRD queries or case files. See the full storage and security notes.
01 / Mental model

What does the lab do?

A documentation passage plays the requirement or PRD role. Source code and tests live in separate SQLite FTS5 indexes. A case correlates all three and asks whether they establish one exact claim.

Searchdocs DBSearchcode DBSearchtests DBVerifyGit + linesBuildcontext packetReviewlocal agentsDecideguardrailSavetrace
Retrieval

Find candidates

Lexical search and a small code-ranking signal suggest passages. A match is a place to inspect, not proof.

Evidence

Verify citations

The runner checks the pinned commit, indexed text, source line range, and context limit. Stale or altered evidence stops the run.

Judgment

Keep opinions separate

Reviewer and critic are sequential prompts to the same local model. Claim-specific checks in lab_guards.py decide the final labels.

Where is RAG?

Retrieval: correlate searches the three FTS5 indexes for candidates. Augmentation: a curated case fetches selected indexed records, verifies them against source, and places their numbered excerpts in the model's context packet. Generation: run --mode local asks the Ollama reviewer and critic to produce JSON judgments from that packet. --mode offline has no generation step.

This is a lexical RAG learning pipeline: no embeddings or vector database. Candidate discovery and case running are separate; the runner does not automatically choose evidence for an arbitrary new PRD line. Its final verdict still comes from the deterministic guardrail, not the model.

02 / Do it yourself

Eight steps, with success signals

The first five steps work without Ollama. The sixth shows how a model error is caught. On a fresh clone, run bash bootstrap.sh first; the README quick start lists prerequisites and explains what it builds.

1

Check the lab is ready

The lab tests exercise pinned-source verification, case verdicts, ranking, RBAC, context limits, and guardrails.

cd ~/prd-code-rag-lab
python3 -m unittest discover -s tests -q
Success: Ran 15 tests and OK.
2

Find a requirement and its possible implementation

The combined query retrieves from three databases. Its suggested links are explicitly marked lexical candidates.

python3 lab.py correlate --repo pluggy --query firstresult --limit 3
Success: requirement docs/index.rst:671-688 and first code candidate _execution._multicall at src/pluggy/_execution.py:89-197. The direct scalar test may be outside the top three.
3

Measure retrieval

Recall@5 asks what fraction of five hand-reviewed targets appear in the top five. MRR@20 rewards targets nearer the top.

python3 benchmark_retrieval.py
Success on pinned indexes: recall_at_k: 0.8 and mrr_at_20: 0.825. Pluggy implementation ranks 1; its direct test ranks 8. This measures ranking, not truth.
4

Prove a correct claim without a model

The case selects exact doc, code, and test citations. The runner verifies all four, builds a bounded packet, and applies its registered proof.

python3 lab.py run --case cases/pluggy_firstresult.json --mode offline
Success: implementation: supports, direct_test_status: established, Evaluation: PASS. Context is about 3,493 of 5,000 characters.
5

Separate a false claim from weak test evidence

One case falsely says the hook returns a list. Another states the true scalar behavior but cites only a no-result test.

python3 lab.py run --case cases/pluggy_firstresult_list.json --mode offline
python3 lab.py run --case cases/pluggy_firstresult_related_test.json --mode offline
Success: first: contradicts / not_established; second: supports / not_established. Both evaluations pass because the final labels match the respective case answer key.
6

Watch the local model and guardrail disagree

Start Ollama in one terminal; use another for the case. The policy expects qwen2.5:1.5b already pulled.

ollama serve
# In a second terminal:
cd ~/prd-code-rag-lab
python3 lab.py run --case cases/pluggy_firstresult_list.json --mode local
Success: final stays contradicts / not_established and evaluation passes. Model wording may vary. In the recorded demo, both agents wrongly supported the list claim; the deterministic proof corrected it.
7

Test an RBAC boundary

The observer can search requirements but cannot read code. This is an application-level exercise; a local user can choose a different CLI principal.

python3 lab.py discover --repo pluggy --kind code --query firstresult --principal observer
Success is a denial: RBAC denied: observer cannot read code evidence and exit code 2.
8

Test the context budget

Try to force a nine-citation Scorecard packet into only 2,000 characters. The builder rejects overflow instead of silently dropping evidence.

python3 lab.py run --case cases/scorecard_branch_protection.json --budget 2000
Success is a denial: Context budget exceeded and exit code 2. Run the same case without --budget to see supports / established and Evaluation: PASS.
03 / Evaluation map

Which check supports what?

A single PASS does not mean every layer succeeded. Read each check as an answer to one narrow question.

CheckQuestionSuccess looks likeDoes not prove
Retrieval benchmarkAre reviewed citations easy to find?4/5 in top five; MRR@20 0.825The candidate supports a claim.
ProvenanceDo index, commit, and source lines agree?Verified citations; case continuesThat genuine text is relevant.
Implementation proofDoes cited code establish the exact claim?supports, contradicts, or insufficientThat a cited test is direct.
Direct-test checkDo cited tests execute and assert this behavior?established or not_establishedThat no better tests exist elsewhere.
Model comparisonDid reviewer and critic agree with final proof?Disagreements recorded in traceTruth; confident models can err.
Case evaluationDo both final labels match the case's expected labels?Evaluation: PASSGeneral accuracy on new claims.
Regression testsAre the known lab behaviors intact?Ran 15 tests … OKThat all upstream project tests ran.

Read this carefully

not_established means the cited tests do not establish the exact claim. A false claim can still earn Evaluation: PASS when the lab correctly labels it contradicts.

04 / Support versus counter-evidence

Six claims, six evidence lessons

HTTPX: five-second default

supports test not established

  • Docs say an unconfigured client uses five seconds.
  • httpx/_config.py:246 sets 5.0; sync and async constructors use that constant.
  • Cited config tests pass 5.0 explicitly or test invalid configuration; neither checks a no-argument client.
Open case JSON

HTTPX: ten-second counterclaim

contradicts test not established

  • The same constant and constructors establish 5.0, which refutes 10.0.
  • The cited tests do not establish a ten-second built-in default.
Open case JSON

Scorecard: Tier 1 score 3

supports test established

  • Docs list force-push and deletion protection as Tier 1.
  • Probe, evaluator, helper, constant, and final-score function make the implementation chain.
  • A table case expects score 3; the cited runner executes and validates it.

Pluggy: first non-None scalar

supports test established

  • Docs describe firstresult behavior.
  • _execution._multicall skips None, stops, and returns results[0].
  • Two cited tests check the scalar and None behavior.

contradicts test not established

05 / Audit the result

Read a JSON trace

After each run, the CLI prints a path under runs/. Open it in your editor. Traces are generated locally and ignored by Git.

Source

repo, commit, and citations tell you exactly which pinned records were used.

Context and agents

context_chars, packet_sha256, and handoffs show the evidence budget and workflow.

Decision

Compare model_opinions, disagreements, final, expected, and evaluation_pass.

Predict before revealing

If the model says a first-result hook returns a list, but cited code returns results[0], what should the final label be?

Reveal answer

Contradicts. The model opinion remains in the trace as a disagreement. The evaluation passes when the deterministic final labels match the case answer key, even when the claim is false.
